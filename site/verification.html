Verification approaches

AI can write code.
Can it help prove it?

That is the bet we are exploring. We are learning what a proof really guarantees, and what it takes to connect one to code people use.

Bring the discipline of proof to AI-written software.

OpenAI’s work on AI and mathematics, including proofs formalized in Lean for computers to check, helped inspire this direction. Could that discipline help us check AI-written code, too?

Assay is an experiment in answering that question. It is not an end-to-end verified database.

A test tries chosen examples. It can catch a mistake, but passing those examples does not show that every other input works.

A proof checks a precise rule. Software checks an argument that the code follows that rule for every input included in the claim.

Start with one question

What is the biggest number?

Teaching example, not a proof result

One passing test can miss a bug.

Imagine a MAX implementation that starts its answer at 0 and only replaces it with a larger number.

Illustrative bug — not an actual Assay defect.

[3, 7, 5] → 7The chosen test passes.

[-3, -7, -5] → 0This is wrong; the maximum is -3.

The code returns 0, but 0 isn’t in the table. That breaks our first rule: the answer must come from the input. A test using negative numbers would catch this mistake. A proof covering negative numbers must account for this case even if we didn’t write that particular test.

What must always be true? What input could expose a mistake? Proposing a missing rule, independently working out a test case, and writing a formal proof are distinct useful contributions. AI-written code and convincing examples do not establish intended behavior. People still need to review whether the specification states the right thing. Contribute technical review →

How we check the code

Two tools. Different jobs.

Kani / actual engine code

Check small, real pieces.

Kani checks selected actual production Rust functions directly. A harness states the allowed inputs and the output rule. Kani looks for a counterexample among all admitted symbolic inputs, not random samples, within its modeled domain and configured exploration limits.

The production-linked multiply_all_i64 harness checks every pair of signed 64-bit integers against the expected product in wider arithmetic. Modeling a small function makes details such as overflow manageable without modeling the whole SQL engine.

Verus / simpler reference code

Prove the SQL behavior clearly.

The fast engine combines SQL behavior with optimization, parallel work and memory details. A simpler executable reference makes the SQL rules and step-by-step proof manageable. It is a separate, slower reference evaluator with proved properties for selected SQL operations. Explore the reference experiment →

The same input: [3, 7, 5]
Next valueWhat the code doesSaved answer
3Read 3. There is no answer yet, so save 3.3
7Read 7. It is larger than 3, so save 7.7
5Read 5. It is smaller than 7, so leave the answer at 7.7

After every step, the saved answer is the largest value read so far.

Verus checks that this reference code establishes the rule, preserves it at each step and returns an answer meeting the specification. These claims cover allowed inputs, not just the three illustrated numbers.

  • [3, NULL, 7, 5] → 7. NULL values are ignored.
  • [] or [NULL, NULL] → NULL. There is no value to choose.

Both methods check code against precise claims; they are not inherently fast-versus-slow tools. Kani does not prove this MAX example, and neither method automatically certifies the whole fast engine. The engine remains experimental alpha; new arithmetic evidence awaits review.

Connecting the two

The fast engine must follow the same rules.

The reference supplies an expected answer for supported queries. The fast engine may process the same rows differently.

What comparison tells us: Cross-checking is testing. The tool checks the same rows, including duplicates, for supported queries where order does not matter. Agreement on this run does not establish agreement for every allowed input.

What we want to prove: Prove the split, local-MAX and combine rule for every allowed input, then show the actual fast code implements those steps. A mathematical merge law alone does not prove the implementation.

Our decision now: performance first.

Proof work takes time. For this project, running optimization and proof work together has been inefficient: changing the engine also changes the code and assumptions a proof must cover.

We are focusing on useful performance first. Then we plan to extend verification of the actual engine, starting with the highest-risk parts and building on the Kani work already done.

Coming: selected components, precise claims and acceptance evidence.

This is the project’s current sequence, not a claim that optimization and verification can never run in parallel.
