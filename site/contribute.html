Start with the public engine.

The engine repository is public. Read the contribution guide, choose a small change, and open a draft pull request. Discuss the scope and evidence with maintainers first.

From a draft to a reviewed change.

  1. Open a focused draft pull request that explains the problem and the change.
  2. Run the local checks in the contribution guide. Share the results, failures and anything you could not run.
  3. A maintainer reviews the change and agrees which checks it needs.
  4. For engine changes, the planned next step is correctness testing and, where relevant, benchmarks on TestMini, our test machine. The results must identify the exact revision tested and be attached or linked to the PR for review.
  5. Maintainers review and accept the required evidence before approving and merging the change. A change that affects execution needs fresh results.

TestMini execution and publication of accepted results are being prepared. They are not operating public automation yet. Documentation-only changes need checks suited to their scope. A package release is a separate decision after merge.

Credit for a merged PR does not certify correctness or accept a benchmark result. Site charts change only when maintainers review and accept new measurements. The current charts keep their historical results.

Development snapshot validation: scoped check results and limitations. These results do not qualify an Alpha 3 release or establish a new performance baseline.

    What appears here

    We check public pull requests for changes to engine or Python binding code, correctness tests, benchmark methods, or formal-verification source files. We use specific file paths, not PR titles, to select changes. Imported Alpha release commits, routine website or setup-only changes, and unmerged work do not count.

    Other commit authors are shown only when GitHub links their authored commits to a public account, with a link to that commit. Bot accounts are labeled separately. Reviews, comments, merge commits and unlinked author names do not establish collaboration here.

    This is recent activity, not a complete contributor directory. We scan the most recently updated closed pull requests and show up to 12 qualifying changes. GitHub limits and unavailable responses can leave the list incomplete. The GitHub link includes all merged pull requests, including website work.

    Bring a result someone else can verify.

    Reproduce one small query.

    Run an example with made-up data on a supported platform. Work out the expected answer independently.

    What acceptance evidence would look like
    • Exact package, platform and Python or Rust version
    • Input, SQL, independently chosen expected answer and actual output
    • Commands and unchanged failure details, if the result differs

    Success means someone else can repeat the check. A passing example is not a general correctness claim.

    Explain one slow query.

    Share a small slow-query example with data you have permission to redistribute. Agree on the benchmark scope with maintainers before comparing a change with its baseline.

    What acceptance evidence would look like
    • Exact revision, machine, dataset, settings and query
    • Before-and-after repeated timings with the same method
    • Correctness checks, resource behavior and any slower cases retained

    A faster result needs a fair comparison, not a single favorable timing.

    Future work on formal verification.

    The separate evaluator and proof workspaces are not public yet. The ideas below are proposals to discuss with maintainers, not instructions for an available proof pipeline.

    Find the case a specification missed.

    Choose one actual-engine component. Ask what must always be true, and which inputs could break that rule.

    What acceptance evidence would look like
    • A precise claim and its allowed input domain
    • Edge cases such as overflow, NULL, empty inputs or duplicate rows
    • A minimal counterexample or reviewable specification change

    Reviewing the right rule is distinct from proving that code follows it.

    Plan a targeted proof or harness.

    Once the relevant sources are available and an engine function is stable, discuss a targeted proof or harness for that function.

    What acceptance evidence would look like
    • Exact production-code connection, tool version and command
    • The theorem or harness, assumptions and exploration limits
    • Machine-check output and what remains outside the claim

    A theorem about a model is not a proof of unconnected production code.
