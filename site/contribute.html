Start with the public engine.

The engine repository is public. Read the contribution guide, choose a small change, and open a draft pull request (PR), which is a proposal to change the code. Discuss the scope and evidence with maintainers in a GitHub issue first. For wrong answers, use the wrong-answer template.

What we need now.

  • Speed: help make large tables practical to analyze. Pick one slow query, then agree on which version to compare and how to time it.
  • SQL coverage: help the engine understand more SQL and return the right answers. Share a small example and work out the expected answer independently.

Verification coverage comes after Alpha 3. Open a focused draft PR after agreeing on scope; follow the contribution guide for local checks and review.

Contribution validation for each PR: our process.

We test the proposed change and the main version separately on the same test computer. Maintainers review the answers, timing and code version before accepting the change. Every PR needs the required test evidence before merge; a green GitHub check alone is not enough.

  • SLT (SQLLogicTest): checks SQL questions against known answers from the SQLite project. We keep the same test collection and report failures as well as passes.
  • hunt55K: asks 55,000 generated questions and compares the answers with independent reference results. Our public generators and test-scope documentation explain what is and is not available.
  • SF10 correctness: checks 22 questions on about 10 GB of data. SF10 is the name for this dataset size. We check answers and resource use before judging speed. See TPC-H background and our input and method limits. These are research measurements, not audited TPC-H results.
  • SF10 timing: repeats those questions using the same tools, data and settings for both versions. We keep practice runs separate from timed runs, report slower queries too, and distinguish the total time from the geometric mean, which gives each query equal weight when comparing time ratios.
  • Retail real-world tests: checks questions about purchases using real and made-up data. It also tests different ways to group products and tricky decimal values. See the UCI Online Retail source and our public SQL and documentation; the public repository does not include raw customer rows or the saved reference answers.

We also run standard code checks and smaller tests. We report unsupported questions, wrong answers, errors and skipped tests separately. If a change could affect execution, we test it again. Technical workflow and evidence rules.

Include reviewed measurements in the same PR as your change, before it is merged. The contribution list shows them after merge. Review documentation and the website for every merge: SQL support, limitations, source versus published packages, and verified results. Include needed updates in the original PR, or explain why no update is needed. Preserve historical results and do not claim measurements for untested builds. After merge, maintainers check the live site against the merged changes. PR6 has been accepted as an experimental change; it is not an Alpha 3 release. Detailed results remain in the qualification report.

What appears here

We include merged changes to engine code, the Python connection, correctness tests, timing methods and proof code. We check the changed files. Website-only changes, setup-only changes, imported releases and unmerged work are excluded.

We also credit authors of code changes when GitHub links them to a public account. Automated accounts are labeled as bots. This list does not track every kind of help, such as reviews or discussions.

This is recent activity, not a complete contributor directory. We scan the most recently updated closed pull requests and show up to 12 qualifying changes. GitHub limits and unavailable responses can leave the list incomplete. The GitHub link includes all merged pull requests, including website work.
