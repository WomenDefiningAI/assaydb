Correctness method and the 37-hour clock

Pilot and full test use different collections. Axes zoom to 31–37h and 90–100%; no earlier result is inferred. The eligible count excludes only control records with no SQL to run, records after a file’s halt instruction, and records marked only for another engine. These exclusions were fixed before execution. Unsupported SQL and unexpected execution or resource errors still count as failures; the full collection retains all records.

Full-run completion times are derived from manifest start time plus recorded elapsed seconds. The clock begins at the first recorded commit, which already contained early work. This is elapsed time, not active coding time or the full project duration. Passing chosen tests is not a proof of all possible inputs.

Now, make 10 GB practical.

Early 1 GB performance showed promise. The larger workload exposes a gap, especially with more workers. We are optimizing toward Polars and DuckDB parity so the engine can be useful for local analysis.

Here, 1 GB and 10 GB mean approximate uncompressed dataset size, not memory use. Performance and production readiness are still work in progress.

Then, verify the riskiest parts of the engine.

Running optimization and proof work together has been inefficient for this project. We are focusing on performance first, then extending targeted verification of actual engine code, building on the arithmetic checks already done.
