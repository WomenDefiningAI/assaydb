A side quest by Helen Lee Kupp

Can AI build a database you can trust?

We are building the part of a database that answers questions about tables. Can AI help us make it fast, reliable and backed by computer-checked proofs?

People guide the work; AI helps write the code in Rust. You ask questions using SQL, a language for working with tables. The engine is an early experiment, not ready for important data.

How we tested

Dates show when we recorded each result, not exactly when the test finished. The points are equally spaced in that order and share one scale. We leave them unconnected because the computers and methods differ.

The Alpha 3 goal is 0.95× Polars on two measures. Total time adds up the query times. The geometric mean combines query-by-query time ratios, giving each query equal weight. We must meet both targets.

The Development Mini points each report one round compared with older Polars timings. We have not verified that those runs used matching sampling rules, excluded practice runs, or kept all five timed repetitions. Fixing the timing code later does not settle that question. Busy-host retries were allowed and may affect the results.

The M2 Pro starting point used three rounds of the command-line engine while other activity was running. It is a different test from the historical M4 result of 4.1364×. Exact methods and limits are linked below.

A separate provisional test on October 15

A separate M4 test reported 0.970× Polars total time and 1.046× geometric mean. This is a provisional result, not accepted performance evidence. It does not meet the 0.95× goal and is separate from the chart points and the Test Mini results.

The test used all 22 queries, 10 workers and three rounds that changed the engine order. Each round included one practice run and five timed runs per query and engine. Estimated 95% intervals were 0.967–0.973× for total time and 1.041–1.048× for the geometric mean. These estimates use three rounds; the fifteen timings are not fifteen independent tests of the computer.

The M4 had 16 GiB of memory. Assay tracked a 4 GiB budget; Polars processed data in smaller batches. Those settings are not equivalent limits on all memory used. Checks for a quiet computer covered six five-second periods, not the whole run. The linked record includes software versions and other settings.

Performance methods, quantitative goals and earlier results

This chart measures command-line code matched to Alpha 2 at revision fb72cc0 on Apple M2 Pro, against DuckDB 1.5.6 and Polars 2.0.0. It is not installed Python-wheel or Python-API timing.

Timing starts with the SQL query and ends when the complete answer is ready in Arrow, a format for storing columns of data. For each query, we took the middle time from five measured runs after a practice run. We repeated this in three rounds, averaged those middle times, and added the query times together. This was a best-effort run with background activity, not a quiet-host baseline. These are research measurements, not audited TPC-H results.

The next goal: 0.95× or less against Polars for both total query time and geometric mean on the same roughly 10 GB, 22-query workload, with correctness checks retained and full settings and results recorded. That is a goal, not an achieved result or a promise about every query.

Earlier small-data results: an earlier engine on Apple M4 used 6.2% less total query time than Polars and 27.1% less than DuckDB at roughly 1 GB with one requested worker. That run is separate from the 37-hour correctness checkpoints and the historical alpha2/M2 Pro chart.

Now, make 10 GB practical.

The larger dataset shows where the engine needs work. We want it to answer useful questions quickly on your own computer. We are improving speed and adding SQL features, while checking that the answers stay correct.

Here, 1 GB and 10 GB mean approximate uncompressed dataset size, not memory use. Performance and production readiness are still work in progress.

Then, verify the riskiest parts of the engine.

A proof must match the code it describes. Because the engine is still changing quickly, we are improving speed and SQL support first. Then we plan to expand computer-checked proofs for the parts most likely to cause serious mistakes.
